# 按摩椅 AI 语音交互模块 —— 设计方案

> 目标：用户对着按摩椅说话 → 理解需求 → 转成按摩椅能执行的动作。
> 平台：ESP32-S3（16MB Flash / 8MB PSRAM），ESP-IDF v6.1.1

---

## 1. 结论：推荐架构

**端侧采集 + 云端理解 + 本地受控执行**，分两块芯片：

```
┌─────────────── 语音模块（ESP32-S3）────────────────┐
│                                                    │
│  I2S 麦克风 ──► AFE（降噪/VAD）──► 录音缓冲(PSRAM) │
│                        │                           │
│                  唤醒词/按键                        │
│                        │                           │
│                   Opus 编码 ──► WiFi ──┐           │
│                                        │           │
│   喇叭(可选) ◄── 预录音频/提示音        │           │
└────────────────────────────────────────┼───────────┘
                                         │
                          ┌──────────────▼───────────────┐
                          │   自有中转服务（你的服务器） │
                          │  ┌────────────────────────┐  │
                          │  │ ASR：语音 → 文字        │  │
                          │  │ LLM：文字 → 结构化指令  │  │
                          │  └────────────────────────┘  │
                          └──────────────┬───────────────┘
                                         │ JSON
┌────────────────────────────────────────▼───────────┐
│  UART / ESP-NOW / RS485                             │
└────────────────────────────────────────┬───────────┘
                                         │
┌────────────────────────────────────────▼───────────┐
│  主控模块（另一块 ESP32）→ 电机 / 气囊 / 加热      │
└────────────────────────────────────────────────────┘
```

**为什么这样分：**

- ESP32-S3 **跑不了**大模型，ASR 和 LLM 必须上云。
- 但**唤醒词和端点检测必须本地做**，否则一直传音频，流量和成本都受不了。
- 语音模块**不直接控制硬件**，只发「意图」，主控负责执行和限幅——这是安全底线。

## 2. 五个关键决策

### 决策 1：ASR 和 LLM 分成两步，不要端到端语音大模型

| 方案 | 延迟 | 可控性 | 成本 | 建议 |
|---|---|---|---|---|
| **A. ASR → 文本 → LLM** | 1.5–2.5s | 高（中间文本可见可测） | 低 | ✅ 一期 |
| B. 音频直接给语音大模型 | 0.5–1.2s | 低（黑盒） | 高 | 二期再评估 |

理由：按摩椅要的是**稳定可控**，中间文本能打印、能回归测试、能加白名单。
端到端语音大模型延迟更好，但输出不稳定、难做安全校验，等产品定型后再考虑。

### 决策 2：一期用「按键触发」，二期再加唤醒词

- 按键方案：**零额外依赖**，今天就能在 IDF 6.1 上跑通全链路。
- 唤醒词：用乐鑫 `esp-sr` 的 WakeNet。注意 **esp-sr 对 IDF 版本敏感**，
  v2.5.0 起才修好 IDF 6.1 的 Kconfig 兼容问题（见[组件更新日志](https://components.espressif.com/components/espressif/esp-sr/versions/2.5.0/changelog)），
  安装时务必指定 `espressif/esp-sr` ≥ 2.5.0。
- 按摩椅场景按键其实很自然：用户坐下 → 按一下 → 说话。先把功能跑通，再谈免手操作。

### 决策 3：云端走**自有中转服务**，不要把厂商 API Key 烧进固件

ESP32 固件的 API Key 可以被 `esptool read_flash` 直接读出来。

```
设备 ──(设备ID + 设备token)──► 你的服务器 ──(API Key)──► 阿里云百炼 / 火山 / 讯飞
```

中转服务的价值：
- 保护 Key，做设备鉴权
- 换模型不用重新刷固件
- 做限流（防刷爆）、用量统计、问题日志
- 可以在服务端升级 prompt，不需要重新出厂

### 决策 4：音频压缩用 Opus，不要传裸 PCM

| 格式 | 比特率 | 5 秒语音体积 |
|---|---|---|
| PCM 16bit/16kHz | 256 kbps | **160 KB** |
| Opus | 16 kbps | **10 KB** |

差 16 倍。按摩椅 WiFi 环境本来就差（电机干扰），必须压缩。
用 IDF 的 `esp_opus` 组件，帧长 60ms。

### 决策 5：两块 ESP32 之间用 UART，长距离/强干扰才用 RS485

| 方式 | 延迟 | 抗干扰 | 适用 |
|---|---|---|---|
| **UART 直连** | <5ms | 一般（短距离、同机箱） | ✅ 首选 |
| RS485 + Modbus | <20ms | 强 | 线缆长、电机干扰大 |
| ESP-NOW | <10ms | 依赖 WiFi 稳定性 | 两板分离、不便走线 |

**按摩椅是大功率电机环境，这点必须重视**：WiFi 在电机启停瞬间可能断流。
所以「语音 → 云端」可以容忍网络抖动，但「语音模块 → 主控」必须是有线链路，
不能因为路由器挂了导致按不动。

## 3. 硬件清单

| 部件 | 型号 | 说明 |
|---|---|---|
| 主控 | ESP32-S3-WROOM-1 **N16R8** | ✅ 你已有：16MB Flash + 8MB PSRAM |
| 麦克风 | **INMP441** | I2S 数字 MEMS，便宜好焊，无 AEC |
| 麦克风（进阶） | ES7210 + ES8311 编解码板 | 双麦 + 硬件 AEC，要边放音边录音就得上这个 |
| 功放（可选） | MAX98357A + 4Ω 3W 喇叭 | 播报用；一期可只用蜂鸣器提示音 |
| 电源 | 5V/1A 独立 LDO | WiFi 峰值电流 500mA，别和电机共用一路 |

**抗干扰措施（按摩椅专属，很重要）：**

1. 音频地和电机地**单点连接**，不要形成地环路
2. 麦克风走线远离电机线束，用屏蔽线
3. 电源入口加 TVS + 大电容（1000µF），吸收电机启停的浪涌
4. 麦克风供电加 LC 滤波
5. 有条件的话，麦克风用**差分** I2S（ES7210 支持）

## 4. 音频链路参数

```
采样率     16000 Hz
位深       16 bit
声道       单声道
帧长       60 ms（Opus 一帧 960 采样）
VAD 静音   700 ms 判定说完
最长录音   10 s（超时强制结束）
```

**内存占用估算（8MB PSRAM 完全够）：**

| 项目 | 占用 |
|---|---|
| WakeNet + AFE 模型/工作区 | ~1–1.5 MB |
| 音频环形缓冲（2 × 32KB） | 64 KB |
| Opus 编码器状态 | ~100 KB |
| 应用其他 | 少量 |
| **合计** | **< 2 MB** |

## 5. 云端接口选型

### 语音识别（ASR）

推荐**阿里云百炼 Paraformer 实时语音识别**：WebSocket 流式，
支持 `run-task` / `finish-task` 事件，边说边出字，延迟低。
（[WebSocket API 文档](https://help.aliyun.com/zh/model-studio/websocket-for-paraformer-real-time-service)）

备选：火山引擎豆包、讯飞语音听写、百度短语音识别。国内延迟都在 200–600ms 量级。

### 大模型（意图解析）

推荐 `qwen-turbo` / `qwen-plus`，用 **JSON 结构化输出**（或 function calling）。
百炼还提供专门的意图识别模型 `tongyi-intent-detect-v3`，更省 token
（[Function Calling 文档](https://help.aliyun.com/zh/model-studio/qwen-function-calling)）。

### Prompt 设计要点

System prompt 必须**锁死输出格式**：

```
你是按摩椅的指令解析器。只输出 JSON，不要任何解释文字。

允许的指令：
{"cmd":"start"}                          开始按摩
{"cmd":"stop"}                           停止
{"cmd":"set_zone","zone":"..."}          部位：neck/back/waist/leg/foot/full
{"cmd":"set_level","level":1-5}          力度
{"cmd":"set_time","minutes":5-60}        时长
{"cmd":"query_status"}                   查询状态
{"cmd":"unknown"}                        听不懂

示例：
用户："脖子好酸"        → {"cmd":"set_zone","zone":"neck"}
用户："力气太大了"      → {"cmd":"set_level","level":2}
用户："来个半小时的"    → {"cmd":"set_time","minutes":30}
用户："帮我订张机票"    → {"cmd":"unknown"}
```

参数：`temperature=0`，`max_tokens=80`。输出越短越稳定，成本也越低。

## 6. 双芯片通信协议

### 帧格式

```
┌──────┬─────┬──────┬─────┬────────┬──────────┬───────┐
│ A5 5A│ ver │ type │ seq │ len(2) │ payload  │ crc16 │
│ 2B   │ 1B  │ 1B   │ 1B  │ 2B LE  │ N bytes  │ 2B    │
└──────┴─────┴──────┴─────┴────────┴──────────┴───────┘
```

| type | 含义 |
|---|---|
| 0x01 | 指令（语音模块 → 主控） |
| 0x02 | 应答（主控 → 语音模块） |
| 0x03 | 心跳（双向，1 秒一次） |
| 0x04 | 急停（语音模块 → 主控，最高优先级） |
| 0x05 | 状态上报（主控 → 语音模块） |

payload 用 JSON，可读、好调试：

```json
{"id":7,"cmd":"set_zone","zone":"neck"}
{"id":7,"ack":true,"err":0}
```

### 三条硬性规则

1. **ACK + 重传**：发出后 300ms 没 ACK 就重发，3 次失败则播报"指令没送到"
2. **心跳看门狗**：主控 3 秒收不到心跳 → **停止所有动作**（安全兜底）
3. **急停直通**：本地识别到"停/停一下/别按了"这类词，**不走云端、不走 LLM**，
   直接发 0x04，全程 <100ms

### 指令白名单（固件里硬编码，LLM 说不动）

```c
zone ∈ {neck, back, waist, leg, foot, full}
level ∈ 1..5          // 超范围直接裁剪
minutes ∈ 1..60
```

**LLM 的输出永远不可信**，必须当作「不可靠输入」来校验：
字段必须存在、类型必须对、枚举必须在白名单内、数值必须裁剪。
校验失败就当 `unknown` 处理，绝不下发。

## 7. 状态机

```
        ┌──────────────────────────────────┐
        │              IDLE                │
        └──┬───────────────────────────────┘
           │ 按键 / 唤醒词
           ▼
      ┌─────────┐   VAD 检测说完   ┌──────────┐
      │LISTENING├─────────────────►│THINKING  │
      └────┬────┘                  └────┬─────┘
           │ 超时 10s                   │ 收到指令
           │                            ▼
           │                      ┌──────────┐
           └─────────────────────►│ ACTING   │
                                  └────┬─────┘
                                       │ ACK / 播报完
                                       ▼
                                     IDLE
```

任何状态异常（网络超时、解析失败、无 ACK）→ 播提示音 → 回 IDLE。

## 8. 延迟与成本预算

| 环节 | 耗时 |
|---|---|
| 唤醒/按键响应 | 100–300 ms |
| 用户说话 | （用户自己决定） |
| VAD 判定说完 | 700 ms |
| Opus 编码 + 上传 | 100–200 ms |
| ASR 最终结果（流式，边说边传） | 300–600 ms |
| LLM 推理 | 400–1200 ms |
| 协议下发 + ACK | <20 ms |
| **合计（不含说话）** | **约 1.6–3.0 s** |

**流量**：一次 5 秒交互 ≈ 10KB 上行。每天 50 次 ≈ 500KB/天，20MB/月。
**成本**：单次交互的 ASR + LLM 费用在**分以下的量级**，商用可忽略（具体以厂商报价为准）。

## 9. 安全与合规

| 风险 | 对策 |
|---|---|
| LLM 生成越界指令 | 白名单 + 类型校验 + 数值裁剪，LLM 输出永不当真 |
| 固件被读取 API Key | Key 只放服务器，走中转鉴权 |
| 断网后无法操作 | 本地固定指令兜底（"停"/"加强"/"减弱"），至少能停 |
| 隐私（录音上云） | 交互前告知；服务端不留音频；可用按键确认代替常驻监听 |
| 电机误动作伤人 | 心跳看门狗 + 急停直通 + 主控侧硬件限位 |

## 10. 分阶段实施

| 阶段 | 内容 | 验收标准 | 预估 |
|---|---|---|---|
| **P0** | UART 协议 + 心跳 + ACK + 急停 | 两块板互发指令，串口能看到 ACK | 1–2 天 |
| **P1** | I2S 麦克风录音，存 WAV 回放 | 电脑上能听清录的语音 | 2–3 天 |
| **P2** | 接云端 ASR，按键说话→打印文字 | 说"我脖子酸"能出正确文字 | 2–3 天 |
| **P3** | 接 LLM，文字→JSON→校验→下发 | 说 20 句不同的话，指令正确率 >90% | 2–3 天 |
| **P4** | 加唤醒词 esp-sr、提示音、兜底逻辑 | 免手操作，断网有提示 | 3–5 天 |
| **P5** | 整机联调 | 电机启停时语音仍可用；连续跑 8 小时 | 1 周 |

**建议先做 P0**：它是唯一不依赖云的部分，做完就能验证两块板的链路，
而且**急停和心跳是整个产品的安全底座**，越早做越好。

## 11. 风险清单

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 电机干扰导致 WiFi 断流 | 高 | 语音不可用 | 电源隔离、音频/电机分地、RS485 链路、离线兜底 |
| esp-sr 与 IDF 6.1 不兼容 | 中 | 唤醒词做不了 | 用 esp-sr ≥2.5.0；实在不行语音模块单独用 IDF 5.5 环境（EIM 可并存多版本） |
| 中文口语识别不准 | 中 | 体验差 | 换模型、加领域词表、prompt 里加示例 |
| 云端服务涨价/下线 | 低 | 业务中断 | 中转层屏蔽厂商差异，随时可换 |
| 误唤醒频繁 | 中 | 烦人 | 提高 WakeNet 阈值；加二次确认（唤醒后播"请讲"） |
