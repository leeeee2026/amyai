## 一、内存 / 泄漏 / 溢出检查

### 1.1 堆分配（全部检查了失败路径）

| 位置 | 大小 | 检查结果 |
|---|---|---|
| `wake_word` rec 录音缓冲 | 187 KB PSRAM | 分配失败会回退内部 RAM，再失败有 null 检查 |
| `wake_word` afe_pcm AFE 输出缓冲 | 187 KB PSRAM | 同上，使用前判空 |
| `tts` 播放管道 | 256 KB PSRAM | 失败有检查，报错退出 |
| `music` 环形缓冲 | 64 KB PSRAM | 一次分配，`music_ensure_ring()` 保证只分配一次 |
| `asr` multipart 请求体 | 约 200 KB 临时 | 所有错误路径都有 `free(body)`，无泄漏 |
| `tts` base64 解码缓冲 | 32 KB 临时 | 所有错误路径都有 `free`，无泄漏 |

### 1.2 缓冲区越界（重点）

| 检查项 | 结论 |
|---|---|
| 录音写 `rec[rec_fill++]` | **已加硬保护**：`if (rec_fill < kRecordSamples)`，越界必不写 |
| AFE 拷贝 `memcpy(afe_pcm + afe_fill, ...)` | 已有 `afe_fill + n <= kRecordSamples` 前置判断 |
| UART 组帧 `build_frame` | 有 `cap < payload_len + 9` 判断，失败返回 0 |
| UART 收帧解析 | 半帧会 break 等待，指针推进受 `i + total <= have` 约束 |
| TTS/音乐环形缓冲读写 | 都先算 `room`/`first = min(len, cap - tail)`，无越界 |
| 诊断用的 `hex[3*32+4]` | `snprintf` 每次写 4 字节、偏移 3 字节，最大写到 96，缓冲 100 字节，安全 |
| 全项目 `strcpy/strcat/sprintf` | **一个都没有**，统一用 `snprintf` |

### 1.3 栈溢出

- 唤醒任务栈 20 KB（云端 TLS 需要），回调里整条 ASR/LLM/TTS 链路都在这上面跑 → 够用
- **新增诊断**：每次处理完一轮打印栈剩余水位，便于长期观察
  `[资源] 唤醒任务剩余栈 xxx 字节 | 内部RAM xxx 空闲 | PSRAM xxx 空闲`
- 提示音任务栈 3~4 KB（只做 delay + 播放调用），开销小

### 1.4 泄漏

- `std::string` 都是栈上对象，作用域结束自动释放
- cJSON 全部配对 `cJSON_Delete` / `cJSON_free`
- HTTP 客户端全部配对 `esp_http_client_cleanup`
- 提示音任务：`args` 结构体在任务结尾 `free`，任务自删除

## 二、并发安全

| 问题 | 处理 |
|---|---|
| 播报时录音把喇叭声录进去 | 加暂停机制，播报期间丢弃音频并重开录音窗口 |
| 暂停标志用 bool 会被重叠播报互相清掉 | **改为计数器**，先结束的任务不会清掉后来者的暂停 |
| 暂停任务异常导致设备永久"失聪" | **加 5 秒超时自恢复**，强制恢复录音 |
| 暂停计数器跨任务读写竞争 | 改用 `__atomic_load_n/store_n` 原子操作（也避开 volatile 自增告警） |
| 提示音任务创建失败 | 判 `pdPASS`，失败打日志，不会留下"永久暂停"状态 |
| 音乐曲目切换新旧任务并存 | **改为严格串行**：旧任务没退干净就拒绝启动新曲目，避免两套任务共用缓冲、旧任务的 `stream_end` 关掉新曲目的流 |
| UART 发送锁 | 超时、组帧失败、免 ACK、正常四种路径都正确 `xSemaphoreGive` |

## 三、性能

| 优化 | 说明 |
|---|---|
| 诊断日志集中开关 | `diag.h` 的 `AMYAI_DIAG_ENABLE`，发布版编译掉，省 CPU 和串口带宽 |
| 诊断峰值统计 | 用 `#if AMYAI_DIAG_ENABLE` 包裹，发布版整段不编进去 |
| 本地识别只喂有效音频 | VAD 给出人声起点，直接喂 `[起点-300ms, 末尾]`，不再喂整段静音 |
| 喂音频上限 3 秒 | 命令词最长 6 字（约 1.5 秒），3 秒足够且不浪费 CPU |
| 离线命中提前返回 | 命中即返回，不走云端，省 4 秒延迟和 API 费用 |

### 实测延迟

| 环节 | 耗时 |
|---|---|
| 录音结束 → 本地识别完成 | 460~630 ms（平均 545 ms）|
| 唤醒 → 播「在的」 | 1.12 s（0.5 s 延迟 + 0.62 s 播放）|
| 本地命中 → 指令下发 | <50 ms |

## 四、遗留风险 / 后续 TODO

1. **提示音播放期间用户说的话会丢**（设计如此：避免串音）。如果以后要支持"打断播报"，需要 AEC 回声消除。
2. **音乐播放任务仍是"停止后等 3 秒"的模型**，极端情况下 3 秒没退干净会拒绝换曲（有日志，不会崩）。
3. **发布版需要手动把 `diag.h` 的 `AMYAI_DIAG_ENABLE` 改成 0**，建议在 CI 或发布脚本里加检查。
4. **主控 ACK 目前关闭**（`CONFIG_AMYAI_UART_REQUIRE_ACK=n`，主控是模拟器）。接真主控后记得打开。

## 五、第二轮自检（流式播报 + 音乐窗口，2026-11-27 下午）

### 5.1 新增的并发安全问题

| 问题 | 后果 | 修复 |
|---|---|---|
| `reply_player` 完成信号被消费两次 | 音乐开始后空等 20 秒才降音量 | 完成标志 `s_done_flag` 做成幂等 |
| TTS 播报期间仍在录音 | 麦克风录到喇叭声，设备把自己讲的笑话当用户输入（自激） | `tts_speak()` 期间 `wake_pause_listening(true)`，暂停超时 5→12 秒 |
| 播报还没结束就开播音乐 | TTS（高优先级）抢占音频通道，音乐任务 write 失败退出 | 音乐分支先 `reply_player_wait_done()` |
| `reply_player` 任务栈占用内部 RAM | 挤爆内部堆 → lwip 分配信号量失败 → DNS 崩在 `memcmp(NULL)` → 重启循环 | 改用 `xTaskCreateWithCaps(..., MALLOC_CAP_SPIRAM)`，栈 12KB 放 PSRAM |

### 5.2 本轮的内存教训

**内部 RAM 是本板最紧张资源**：连网前 130KB，连网后仅 ~50KB（WiFi + TLS 都从这里要）。

新增任务一律把栈放 PSRAM：

```c
xTaskCreateWithCaps(task, "name", 12 * 1024, arg, prio, NULL, MALLOC_CAP_SPIRAM);
```

同时把 `asr_init` 任务栈从 10KB 降到 8KB（只加载模型，不跑 TLS）。

### 5.3 新增的健壮性检查

| 检查项 | 结论 |
|---|---|
| `reply_player` 队列项 | 全部 `free`，begin 时清空残留，队列满丢弃并记日志 |
| 句子切分越界 | 按 UTF-8 多字节标点处理，下标推进受长度约束 |
| JSON 清洗 | `\'` → `'`（模型偶尔输出非法转义，会让整条回复解析失败）|
| JSON 解析失败 | 不播兜底语（会打断已播内容）、不下发指令 |
| `tts_speak` 暂停配对 | 用 RAII 守卫，任何返回路径都会恢复录音 |

### 5.4 性能

| 优化 | 效果 |
|---|---|
| LLM 流式 + 首句即播 | 云端闲聊 4.5s → 2.9s |
| ASR/TTS/LLM 连接复用 | TTS 首包 1155ms → 603ms 平均 |
| 本地识别喂音频 3s → 2s | 短命令识别快一点（实测语音段普遍 <1s，上限基本不触发）|
