# 硬件真相与音频问题排查（2026-11-26 更新）

> 这份文档纠正了之前几个**错误的假设**。如果你看到旧代码/旧文档里提到 ES8311，那是历史遗留，实际硬件不是那样。

## 一、板子的真实音频硬件（DNESP32S3B）

以 `DNESP32S3B开发板+V1.0+硬件参考手册.pdf` 第 19 页原理图为准：

```
音频输出：U6 = NS4168（I2S 数字输入，单声道 D 类功放，3W @ 5V）
    引脚 1 CTRL  ← SPK_CTRL（XL9555 的 IO0_5，5.1K 下拉）
    引脚 2 LRCLK ← IO13
    引脚 3 BCLK  ← IO21
    引脚 4 SDATA ← IO14
    引脚 5/8 VoN/VoP → 板载 8Ω 1W 喇叭

音频输入：U8 = MSM261S4030H0R（数字 I2S 麦克风）
    引脚 3 WS  ← IO13
    引脚 6 SCK ← IO21
    引脚 7 SD  → IO47
    L/R 引脚接 VCC3.3（数据只出现在右声道槽位）
```

**关键结论：**

1. **板子上没有 ES8311（或其他 codec 芯片）。** I2C 扫描只发现 0x18/0x1E/0x20/0x2E/0x50/0x6A，没有 0x30。
   - 曾经花了很久调 "ES8311 DAC 音量寄存器 REG32"，全是写给不存在芯片的，**无效**。
   - 音频音量 100% 由 **I2S 数字电平** 决定，没有 DAC 音量寄存器可调。

2. **功放使能 = XL9555 IO0_5 拉高。** NS4168 的 CTRL 引脚：
   - < 0.4V → 关断
   - 0.9~1.15V → 左声道
   - 1.5V~VDD → 右声道（使能）
   
   代码里 `pa_set(true)` 拉高是对的。

3. **麦克风是数字麦，数据直接走 I2S DIN(IO47)。** 不需要配置 codec 的 ADC 模式。

## 二、"麦克风断流 → 重启" 的真正原因（P0 bug）

**不是硬件，也不是麦克风增益。**

`wake_word.cpp` 里的声道判定：

```c
int left_energy = 0, right_energy = 0;   // run() 里只声明一次，永不清零
...
left_energy += le;                        // 每个 I2S 块累加
right_energy += re;
const bool use_left = (left_energy >= right_energy);
```

每块 512 帧，左声道均值约 150 → 每秒累加 `44100 × 150 ≈ 6.6e6`
→ **约 322 秒后 int32 溢出变负** → `use_left` 翻成 false → 选到全 0 的右声道
→ 1 秒后判定"麦克风无信号" → `esp_restart()`

**历史日志完全吻合：**

| 日志 | 用左→用右 | 重启时间 |
|---|---|---|
| `_mpifix.log` | 310.5s | 319.5s |
| `_musicfix.log` | 149s | 151s |
| `_m3.log` | 170s | 172s |
| `_ack.log` | 494s | 496s |

**修复：** 开机统计 1 秒（86 个块）投票，然后**锁定声道**，运行期不再切换。

```c
if (!ch_locked) {
    if (le > re) ++ch_vote_left; else if (re > le) ++ch_vote_right;
    if (ch_vote_left + ch_vote_right >= 86) {
        use_left = (ch_vote_left >= ch_vote_right);
        ch_locked = true;
    }
}
```

实机日志：`麦克风声道锁定：左声道（左票 86 / 右票 0）`

> 注意：原理图写 L/R 接 VCC3.3 = 右声道，但实测数据在**左**槽位。以实测为准（已锁定）。

## 三、其他已修复的音频问题

| 问题 | 原因 | 修复 |
|---|---|---|
| TTS 每句尾音被截断 | `stream_end` 与播放任务并发，`s_out` 被 memset | 加 `inflight` 计数，等真正写完再收尾 |
| 唤醒应答「在的」在放音乐时丢失 | 音乐流整段持有音频锁，提示音等 3 秒超时 | `play_pcm`/`stream_begin` 先设置抢占标志，让低优先级流主动退出 |
| TTS 分片被误丢 | 拿 base64 长度和解码缓冲大小比较（实际只有 3/4）| 按解码后长度判断 |
| 音乐拉流失败后"幽灵播放态" | 预缓冲死等，不检查 eof | 加 5 秒超时 |
| 降采样周期性失真（约 86Hz）| `(int)pos` 对负相位向 0 截断，产生外推 | 改用 `floor` |
| 音乐 ducking 把 TTS 也压小 | 直接改全局音量 | 新增 `audio_hub_set_music_volume()`，只压音乐 |

## 四、已知但暂未修复

| 优先级 | 问题 | 影响 |
|---|---|---|
| P0 | 音乐 reader/player 双任务无代际管理 | 切歌时旧 reader 可能残留、共享 ring/静态缓冲、`std::string s_url` 跨任务无锁 |
| P1 | 重采样每样本用 `double`（S3 无 double FPU，全软件模拟）| 播放期间 CPU 热点，和 WiFi/TLS 抢 CPU |
| P1 | 44.1k→16k 降采样无抗混叠低通 | 8k 以上能量混叠进语音频段，影响唤醒/识别率上限 |
| P2 | 若干死代码、忙等轮询 | 可维护性问题 |

## 五、教训

1. **先查原理图，再动代码。** 我们对着不存在的 ES8311 调了半天音量寄存器。
2. **日志时间戳会说话。** 多个日志里"用左→用右→重启"的时间间隔都在 320 秒左右，这是溢出的指纹。
3. **别用累加变量做实时判断。** 需要滑动窗口或定期清零。
4. **文档里的硬件描述要能和原理图对上。** 旧文档写 ES8311 + 模拟麦，实际是 NS4168 + 数字麦。
