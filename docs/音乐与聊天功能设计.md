# 音乐播放 + 语音聊天 功能设计

> 需求：在现有「语音控制按摩椅」之外，增加
> ① 听歌  ② 聊天（含产品介绍、天气等闲聊）
>
> 这两个功能会把现在的"单向播提示音"升级成**真正的音频子系统**，
> 是本次改造里工作量最大的一块。

---

## 1. 现状与差距

| 能力 | 现在 | 需要 |
|---|---|---|
| 音频输出 | 只能播一段 0.48s 的预录「在的」 | 要能播任意长度音频（TTS/音乐） |
| 文本转语音 | **没有** | 聊天必须把模型回答念出来 |
| 音乐解码 | **没有** | MP3/AAC 解码 + 文件/流读取 |
| 音频通道仲裁 | 没有（只有提示音） | 提示音/TTS/音乐并存，要分优先级 |
| 意图分类 | 全部当控制指令 | 要区分 控制/聊天/音乐/介绍/天气 |

---

## 2. 总体架构

### 2.1 一句话的流向

```
唤醒 → 录音 → ASR → 意图路由（一次 LLM 调用）
                        ├─ control  → v2 指令 → UART → 主控执行
                        ├─ chat     → 对话回复 → TTS → 喇叭
                        ├─ intro    → 产品介绍文本 → TTS（或预录音）
                        ├─ weather  → 拉天气 → 组织回答 → TTS
                        └─ music    → 音乐控制（播/停/下一首/音量）
```

**关键决策：意图路由和指令解析合并成一次 LLM 调用**，减少一次网络往返（省 1–2 秒）。
做法是让模型输出带 `intent` 字段的 JSON：

```json
{"intent":"control","actions":[{"cmd":"set_zone","zones":["shoulder"]}]}
{"intent":"chat","reply":"今天北京晴，18 到 26 度，适合出门。"}
{"intent":"music","action":"play","query":"轻音乐"}
{"intent":"intro"}
```

### 2.2 音频通道（核心改动）

现在只有一个 I2S TX，所有声音都得排队：

```
                 ┌─────────────────────────────┐
  提示音(在的) ──→│                             │
  TTS 播报    ──→│   AudioHub（优先级仲裁）     │──→ I2S TX ──→ NS4168 ──→ 喇叭
  音乐        ──→│   + 音量控制 + ducking       │
                 └─────────────────────────────┘
```

优先级（高 → 低）：

1. **急停提示音**（"已停止"）
2. **唤醒应答**（"在的"）
3. **TTS 播报**（聊天/介绍/天气回答）
4. **音乐**

规则：

- 高优先级抢占时，低优先级**压低音量（ducking）**而不是直接停，回来后恢复
- 播放 TTS 期间**暂停唤醒检测**（否则自己的声音会触发唤醒）
- 音乐播放时唤醒词仍要能响应 → 音乐 ducking 到 30%

### 2.3 边放边听（AEC）

严格来说，"放音乐时还能被唤醒"需要 **AEC（回声消除）**：把播放的数据作为参考信号喂给 AFE。

- esp-sr 的 AFE 支持 AEC，但需要**双通道输入**（MIC + 参考）
- 当前配置是 1MIC，要改成 1MIC + 1REF
- 这块需要单独调试，**建议二期再做**；一期采用"放音乐时降低音量、唤醒后暂停音乐"

## 3. 音乐播放

### 3.1 三种音源

| 方案 | 实现难度 | 优点 | 缺点 |
|---|---|---|---|
| **TF 卡本地** | 低 | 稳定、无网络依赖、音质好 | 要拷文件，曲库固定 |
| **HTTP 直链/电台** | 中 | 曲库无限、可运营 | 依赖 Wi-Fi，断流要处理 |
| **蓝牙 A2DP Sink** | 高 | 手机直接推歌 | 内存占用大，和 BLE 配网/唤醒抢资源 |

**建议一期做「TF 卡 + HTTP 直链」两种**，共用同一套解码管线：

```
读文件/HTTP → esp_audio_codec 解码 → PCM → AudioHub → I2S
```

板子已有 TF 卡接口，且 16MB Flash 可以放几首内置试听曲。

### 3.2 需要的组件

- `espressif/esp_audio_codec`（MP3/AAC/FLAC 解码）
- `espressif/esp_gmf` 的 audio_render（可选，简化管线）
- 文件系统：`esp_vfs_fat` + SDMMC

### 3.3 音乐指令（v3 新增）

| cmd | 参数 | 说明 |
|---|---|---|
| `music_play` | `query` 可选 | 播放（可带风格/歌名） |
| `music_pause` / `music_resume` | — | 暂停/继续 |
| `music_next` / `music_prev` | — | 切歌 |
| `music_stop` | — | 停止 |
| `set_volume` | `level` 0–100 | 音量绝对值 |
| `adjust_volume` | `delta` -20..20 | 音量相对 |

## 4. 聊天与 TTS

### 4.1 TTS 选型

| 方案 | 延迟 | 成本 | ESP32 集成难度 |
|---|---|---|---|
| **智谱 glm-tts** | 1–2s/句 | 按字符计费（需确认） | 低：一次 HTTP POST 拿音频 |
| 阿里云 CosyVoice | 可流式，首包快 | 有免费额度 | 中：签名复杂 |
| 火山引擎 TTS | 可流式 | 有免费额度 | 中 |
| 微软 Edge TTS | 低 | 免费 | 高：WebSocket 协议，ESP32 上麻烦 |

**建议用智谱 `glm-tts`**：和现有 ASR/LLM 同一把 Key、同一个域名、同样鉴权，集成成本最低。

接口（待实测确认参数名）：

```
POST https://open.bigmodel.cn/api/paas/v4/audio/speech
{
  "model": "glm-tts",
  "input": "今天北京晴，18 到 26 度",
  "voice": "tongtong",
  "response_format": "wav",     // 或 mp3 / pcm
  "speed": 1.0
}
→ 返回音频二进制
```

**关键**：优先请求 **PCM/WAV 16k 单声道**，这样可以跳过解码器直接送 I2S；
如果只能给 MP3，就用 esp_audio_codec 解。

### 4.2 延迟预算（聊天场景）

| 环节 | 耗时 |
|---|---|
| 录音（固定 4 秒，已有） | 4.0 s |
| ASR | ~1.2 s |
| LLM 生成回答 | ~1.5–3 s（回答越长越慢） |
| TTS 合成 | ~1.0–2 s |
| 播放首字 | 立即 |
| **用户感知总延迟** | **约 8–10 秒** |

> 这是"录音 4 秒固定"造成的硬伤。聊天场景建议**改成 VAD 自动断句**（说完就停），
> 能把录音时间从 4 秒压到 1–2 秒。

### 4.3 对话上下文

- 保留最近 **3–5 轮**对话（放 PSRAM）
- 超过 20 轮清空，避免 prompt 无限增长
- 唤醒后如果 30 秒没说话，上下文重置

### 4.4 产品介绍

两种做法，建议**组合**：

1. **主介绍用预录音**（30–45 秒）：音质最好、零延迟、离线可用
   > "我是 XX 按摩椅的语音助手。你可以直接对我说，比如：按按肩膀、力度重一点、
   > 腿抬高一点、开个热敷、来个二十分钟……"
2. **追问用 TTS**：用户问"还能干什么"、"热敷怎么开"这种，交给 LLM 用 TTS 回答

介绍文案要**可配置**（存在 NVS 或 TF 卡里），换产品不用重新烧固件。

## 5. 天气

### 5.1 数据来源

| 方案 | 说明 |
|---|---|
| **和风天气** | 免费版 1000 次/天，需注册 Key，返回 JSON |
| **心知天气** | 类似 |
| 让 LLM 直接答 | ❌ 模型不知道实时天气，会瞎编 |

### 5.2 流程

```
用户："今天天气怎么样"
  → 取缓存的天气（每 30 分钟更新一次）
  → 注入到聊天 prompt：
    "当前天气数据：北京，晴，18-26℃，湿度 45%，AQI 62。回答时用口语，不要念 JSON。"
  → LLM 生成自然语言
  → TTS 播报
```

**城市来源**：配网时由手机 App 下发（或从路由器获取不到，必须用户给）。

## 6. 指令集 v3 扩展

在 v2 基础上新增：

```json
{"intent":"control", "actions":[...]}      // 原 v2 指令，包一层 intent
{"intent":"chat",    "reply":"..."}
{"intent":"intro"}
{"intent":"weather", "city":"北京"}         // city 可省略，用配置的默认城市
{"intent":"music",   "action":"play|pause|resume|next|prev|stop", "query":"..."}
{"intent":"volume",  "delta":-1}            // 或 "level":50
```

> `intent` 字段是这次改造的核心：**先分类，再执行**。
> 老版本固件收到没有 `intent` 的 JSON 时，按 `control` 处理，向后兼容。

## 7. 工作量与风险

| 模块 | 预估 | 风险 |
|---|---|---|
| AudioHub（优先级 + ducking + 音量） | 2–3 天 | 中：多任务抢 I2S 要仔细设计互斥 |
| TTS 接入（HTTP + 播放） | 1–2 天 | 低 |
| 音乐播放（TF 卡 + MP3 解码） | 3–4 天 | 中：解码 + 文件系统 + 断点续播 |
| 意图路由（prompt 改造） | 0.5 天 | 低 |
| 对话上下文管理 | 1 天 | 低 |
| 产品介绍预录 + 配置化 | 1 天 | 低 |
| 天气接入 | 1 天 | 低 |
| **VAD 自动断句**（强烈建议） | 2 天 | 中：影响交互流畅度 |

**总计约 10–14 人天**。
