## 二、分阶段实测数据

### 云端闲聊（「讲个笑话」）

```
录音结束
  → 本地 ASR 未命中      530 ms   （空跑，命令词走本地才值）
  → 云端 ASR 完成        335 ms
  → LLM 首字            1091 ms   （正常网络 639 ms）
  → TTS 首包出声        1109 ms   （后续句子 508 ms）
  ────────────────────────────
  录音结束 → 出声       3600 ms   （正常网络约 2900 ms）
```

### 本地命令词

```
录音结束 → 识别完成：470 ~ 650 ms（平均 560 ms）
          + 延迟 500ms 播报「好的，马上为您调整」
```

> 说明：本地识别耗时 ≈ 喂入音频长度 × 0.33。喂入长度由 VAD 切出的语音段决定
> （说完 + 450ms 静音就停），所以短命令本来就快。

## 三、做了什么

### 1. 连接复用（ASR / TTS / LLM）

每次请求都重建 TLS 要 400~600ms。改成常驻客户端 + keep-alive。

**踩的坑**：连接复用时 `cfg.user_data` 固定为 `nullptr`，必须用全局指针
`s_cur_ctx` / `s_cur_stream` 在每次请求时指向当次上下文。
**漏改一处，SSE 数据就全被丢弃**（表现为"所有语音都没了"、"大模型调用失败"）。

### 2. LLM 流式 + 首句即播

```
请求 stream:true → 逐块解析 SSE → 增量提取 reply → 切句 → TTS
```

- 提示词改成 **reply 优先**（reply 永远是第一个字段），才能边收边播
- 44 条测试集 A/B：旧版 90.9% → reply 优先版 97.7%
- 抖动缓冲：拿到第一句先等 250ms 攒后续，网络抖一下不会卡
- 实测：LLM 首字 639ms 时 TTS 已经开始出声（比 LLM 收完早）

### 3. 提示词精简（实测证明不划算）

| 版本 | 字符数 | 全对率 | 平均延迟 |
|---|---|---|---|
| 精简版 | 1392 | **79.5%** | 1465 ms |
| 完整版 | 1883 | 93.2% | 1835 ms |
| 修正版（当前）| 2338 | **100%** | 1714 ms |

省下的 prefill 完全被网络抖动（600~3500ms）淹没，而准确率掉 13.7 个点。
**结论：不要为省 token 砍提示词，靠连接复用和流式降延迟。**

### 4. 音乐窗口重构

音乐播放时麦克风主要听到音乐，ASR 出来的全是碎片（"听不清"、"Okay."）。
旧逻辑把这些碎片送去云端，会产生"请再说一遍歌曲名"这类莫名回复，甚至误判成放歌。

新逻辑 —— **音乐窗口完全不调云端**：

| 你说 | 结果 |
|---|---|
| 停 / 关掉 / 停止 | 直接停，静默 |
| 换一首 / 下一首 / 上一个 | 直接换歌，静默 |
| 其他任何内容 | 忽略，音乐继续 |

配套改动：
- ducking 音量做成 Kconfig（`AMYAI_MUSIC_DUCK_PERCENT`，默认 40%，原硬编码 20% 太小）
- 音乐窗口说话阈值 `8000` → `max(底噪*3, 3500)`（40% 时漏音约 2000，人声约 4000）
- `music` 意图的 `reply` 必须为空字符串（放歌/换歌/停止都不播报）

## 四、本轮修的关键 bug

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 流式版所有语音消失 | SSE 回调没走全局 ctx 回退，`user_data=nullptr` 导致数据全丢 | 加 `s_cur_ctx` / `s_cur_stream` 回退 |
| 2 | 讲笑话被中断、冒兜底语 | `max_tokens=64` 截断长回复 → JSON 非法 → 播"这个我不太确定"抢占音频 | max_tokens 220 + 清洗 `\'` + JSON 失败不播兜底 |
| 3 | 设备自己念段子又"听"到了 | 播报期间没暂停录音，麦克风录到喇叭声当用户输入 | `tts_speak()` 期间暂停录音 |
| 4 | 说了没反应，要说好几遍 | VAD 掉音即清零，凑不满"连续 10 块" | 改为衰减 2；阈值 2500→2200 |
| 5 | 音乐开始 20 秒后才降音量 | `reply_player_wait_done` 完成信号被消耗两次，第二次空等满超时 | 完成标志做成幂等 |
| 6 | 音乐一开始没降音量（更早）| 流式播报还在响时开播音乐，TTS 抢占音频通道 | 音乐分支先等播报结束 |
| 7 | 停止音乐还回"停啦" | 模型给 stop 指令生成了回复 | 提示词要求起停指令 reply 为空 |

## 五、内部 RAM 教训（重要）

ESP32-S3 这块板**内部 RAM 是最紧张资源**：连网前 130KB 空闲，连网后只剩 ~50KB
（WiFi + TLS 都要从这里要）。

**新增任务一律把栈放 PSRAM**：

```c
xTaskCreateWithCaps(task, "name", 12 * 1024, arg, prio, NULL, MALLOC_CAP_SPIRAM);
```

血泪教训：给流式播放任务开了 6KB 内部 RAM 栈，直接把堆挤爆，
导致 lwip 分配信号量失败 → DNS 解析崩在 `memcmp(NULL)` → 重启循环。

## 六、还能做但没做的优化

| 方案 | 收益 | 为什么没做 |
|---|---|---|
| 开机预热 LLM/TTS 连接 | 首次交互 -600ms | 用户不需要 |
| 本地 ASR 与云端 ASR 并行 | -530ms | 命令词会浪费云端调用（花钱）|
| AEC 回声消除 | 音乐可 100% 播放仍能识别 | 需参考信号对齐调试（1~2 天），且单麦效果有限、内部 RAM 有风险 |
| 本地词表扩覆盖 | 更多话走本地（-3.5s/条）| 靠维护 `docs/离线命令词表.md` 逐步补 |
